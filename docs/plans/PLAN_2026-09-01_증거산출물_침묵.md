# 라운드 14 — 증거 산출물이 조용히 비어 있었다

## 착수 실측 (추측 아님 — 전부 재현했다)

라운드 12~13 에서 `unmatched_headings` 선택지를 만들었다. 그 선택이 **증거 산출물**에
어떻게 남는지 재 보니, 서로 독립인 결함 3건이 나왔다.

재현: `scratchpad/r14_probe_validation.py` — SwUFn 절 5개 템플릿(alpha 만 payload 에 있음)
으로 `keep`/`drop` 각 1회 생성 후 `.validation.md` 를 실제로 만들어 읽었다.

### F1 — `drop` 이 "빈 heading" 을 **증거에서 지운다**

| `.validation.md` | keep | drop | 실제 |
|---|---|---|---|
| SwUFn headings | 5 | **2** | 템플릿엔 5 |
| ⚠ 데이터 없는 템플릿 heading | **4건** | **1건** | 여전히 4 (3개는 제거됨) |
| Tables / Images | 5 | **2** | — |
| OK | True | True | — |
| "제거했다" 는 문장 | — | **없음** | — |

`.validation.md` 는 **문서와 payload 사이드카만** 읽는다. `drop` 이면 대응 소스가 없는
heading 이 문서에서 사라지므로 "빈 명세" 경고가 줄고, 리포트는 거의 완결된 문서로 보인다.
이 저장소가 반복해 고쳐 온 **절단의 침묵**이고, 증거 번들(`evidence.py`)에 실려 나가므로
ISO 26262 근거로 읽힌다.

지운 수(`dropped_heading_count`)와 모드는 이미 `<out>.docx.gen_stats.json` 에 있다
(라운드 12 에서 넣었다). 검증기가 그걸 **안 읽을 뿐**이다.

### F2 — 증거 리더의 세 필드가 **한 번도** 채워진 적이 없다

`evidence.py:254-256` 은 영문 키를 찾는다:

```python
"expected_functions": _as_int(head.get("Expected functions")),
"matched_functions":  _as_int(head.get("Matched functions")),
"missing_from_docx":  _as_int(head.get("Missing from docx")),
```

라이터(`validation.py:297-308`)가 쓰는 것은 한국어다: `Payload 함수 수` ·
`문서에 실린 함수(매칭)` · `⚠ 문서에 없는 소스 함수`. 저장소 전체에서 영문 3키를 쓰는
**writer 는 0곳** — 즉 세 필드는 영구 `None` 이다. 실측:

```
keep {"expected_functions": null, "matched_functions": null, "missing_from_docx": null}
drop {"expected_functions": null, "matched_functions": null, "missing_from_docx": null}
```

소비처 `DocGenStatusBoard.jsx:1415` 의
`{val.missing_from_docx != null && ' · 문서에 빠진 함수 N개'}` 는 **렌더된 적이 없다**.

값 파싱도 따로 깨져 있다: 라이터가 backtick **안**에 단위를 넣어(`` `120건` ``)
`_as_int` 가 `None` 을 낸다. 키를 고쳐도 값이 안 들어온다 — 두 겹이다.

이 모듈의 docstring 이 "writer 는 4곳인데 reader 는 0곳이라 화면이 한 번도 본 적이 없다"
라고 자기 존재 이유를 적어 두었는데, **한 층 아래에서 같은 결함이 재발**했다.

### F3 — 가장 중요한 완결성 수치를 리더가 아예 안 읽는다

라이터는 `⚠ 데이터 없는 템플릿 heading: \`4건\`` 을 쓰지만 리더에 대응 키가 **없다**.
빈 명세로 나간 heading 수는 "이 문서가 껍데기인가" 의 직접 지표인데 화면에 닿지 않는다.

### 왜 테스트가 못 잡았나

`test_quality_evidence.py::test_fields_absent_in_old_reports_are_none_not_zero` 는
**손으로 쓴 구판 .md** 를 먹여 `is None` 을 단언한다. 결함이 있든 없든 통과한다 —
관측량을 단언하지 않는 가드다. 프론트 `DocGenStatusBoard.test.jsx:211` 은
`missing_from_docx: 9` 라는 **파이프라인이 만들 수 없는 shape** 을 손으로 넣어 통과한다.

빠진 것은 **왕복 검사**다: 진짜 라이터 → 진짜 리더 → 수치 복원.

## 개선

### 작업 1 — 라벨 단일 출처 (F2·F3 근본)

`report_gen/validation_labels.py` **신설**(무의존). 라이터·리더가 같은 상수를 쓴다.
문자열을 양쪽이 각자 들고 있는 한 같은 결함이 다시 난다 — 이번 세션이 이미 두 번 겪었다.

- 라이터: 상수 사용 + 단위를 backtick **밖**으로(`` `120`건 ``).
- 리더: 상수 import, 키에서 선행 `⚠` 정규화, 구판 `` `120건` `` 도 읽는 `_as_count`.
  (구판 산출물이 디스크에 남아 있으므로 관용은 유지한다.)

### 작업 2 — 제거 사실을 증거에 싣는다 (F1)

`validate_uds_docx_structure` 가 `gen_stats_path(docx)` 사이드카를 읽어
`dropped_heading_count` · `unmatched_headings_mode` 를 결과·리포트·경고에 싣는다.

- 사이드카 부재 → 둘 다 `None`, 줄도 경고도 없음. **모드를 추정하지 않는다**
  (`keep` 으로 가정하면 '제거 없음' 이라는 거짓이 된다).
- `dropped > 0` 이면 "위 '데이터 없는 heading' 수치는 **남은 것만** 센다" 를 명시.
- `ok` 판정은 **건드리지 않는다** — 부분집합 템플릿이 의도일 수 있다는 기존 결정 유지.

### 작업 3 — 화면

`DocGenStatusBoard.jsx` 근거 줄에 빈 heading / 제거 heading 을 싣는다.

### 작업 4 — 왕복 가드

`tests/unit/test_validation_report_roundtrip.py` 신설: 진짜 문서를 만들고
진짜 `.validation.md` 를 쓴 뒤 `read_docx_validation` 이 **수치를 복원**하는지 단언.
`drop` 산출물에서 제거 수가 증거에 남는지도 같이 단언.
기존 구판 테스트는 **음성 대조군으로 유지**한다(부재는 여전히 `None` 이어야 한다).

## 리스크

- `.validation.md` 형식이 바뀐다. 리더는 1곳뿐이고 구판 관용을 유지하므로 회귀 없음.
  사람이 읽는 문장은 단위 위치만 바뀐다.
- `validation.py` → `validation_labels.py` 는 무의존이라 `evidence.py` 의 경량성
  (python-docx 없이 동작)이 유지된다. 반대 방향(evidence→validation) 이면 깨진다.
