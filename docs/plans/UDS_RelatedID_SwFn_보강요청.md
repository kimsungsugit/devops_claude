# UDS `Related ID` 보강 요청 — SwCom 유지 + SwFn 병기

> **이 문서의 위치** — ARIA(추적성 자동화 도구) 측이 **문서 작성 파트에 보내는 요청**이다.
> 도구가 스스로 고칠 수 없는 것, 즉 **설계 의도**를 문서에 적어 달라는 요청만 담는다.
> 대상 프로젝트: **KJPDS02** / 기준 문서: `SwUDS v3.02_260XXX`, `SwDS v3.01_20260410_R`
> 작성일: 2026-07-30 / 대조 기준 커밋: `10d9aa5`(설계-ID 브리지), `52e4b08`(함수 fan-out 차단)
> 모든 수치는 원문 직접 파싱 실측이며, 재현 스크립트 경로를 §6에 남긴다.

## 0. 한 줄 요약

UDS `Related ID` 열에 **기존 `SwCom_NN` 을 그대로 두고 `SwFn_NN` 을 함께 적어** 주시기 바랍니다.
대상은 **앱 기능 계층 390행**입니다(부록 A).

**SwCom 을 SwFn 으로 교체하는 것은 안 됩니다** — SwFn 에는 ASIL 표기가 없어 안전등급 근거가 사라집니다(§4).
**함수 하나에 SwFn 하나**가 원칙입니다 — 여러 개 나열하면 추적 변별력이 지금보다 나빠집니다(§3).

> **⚠ 2026-07-31 대상 재산정.** 초판은 SwCom 만 적힌 **900행 전체**를 대상이라 적었습니다.
> 계층별로 분해하니 그중 **256행이 부트로더·드라이버·라이브러리**였습니다. 여기에 앱 설계ID를
> 붙이면 "부트로더가 Assist Close 요구를 구현한다"는 거짓 추적이 문서에 박힙니다.
> 대상을 **앱 계층 390행**으로 좁혔고, 제외한 256행은 **부록 D 에 근거를 남겼습니다.**

## 1. 현황 실측

`SwUDS v3.02` 의 함수별 표 **1,035개**를 전수 파싱한 결과입니다.

| 항목 | 실측 |
|---|---|
| `Related ID` 열 존재 | ✅ 있음 (전 1,035행) |
| 값이 채워진 행 | **1,035 / 1,035 (100%)** — 빈 칸 0 |
| SRS 요구ID(`SwTR_`/`SwEI_`/`SwTSR_`…)를 담은 행 | **0** |
| `SwCom_NN` 만 적힌 행 | 900 (87.0%) |
| `SwFn_`/`SwSTR_`/`SwST_`/`SwTK_` 를 포함한 행 | 135 (13.0%) |

즉 열도 있고 값도 다 차 있습니다. **입도(粒度)만 컴포넌트 수준**입니다.

| └ 병기가 필요한 행 | 646 | |

## 2. 왜 필요한가 — SwCom 은 추적 연결에 쓸 수 없습니다

추적성 도구는 `UDS 함수 → 설계ID → SDS → SRS 요구` 경로로 역추적합니다. 그런데 **SwCom 은 이
경로에서 구조적으로 제외**되어 있습니다. 임의 결정이 아니라 실측 근거가 있습니다(커밋 `10d9aa5`):

> SwCom 을 브리지에 포함하면 도달하는 요구 수는 **그대로(64)** 인데
> 요구당 연결 함수 수(fan-out) 중앙값이 **22 → 56 으로 악화**된다.

SwCom 은 컴포넌트 하나가 요구 수십 개를 한꺼번에 참조하는 **느슨한(loose) 노드**라, 넣으면
"이 요구에 이 함수 500개가 관련됨" 같은 무의미한 연결만 늘어납니다.

**결과**: SwCom 만 적힌 행은 이 경로에서 빠집니다. 문서에 값이 있는데도 도구가 쓰지 못하는
상태입니다.

다만 **900행 전부가 미추적은 아닙니다** — 함수명이 SwDS 함수 항목과 같으면 도구가 이름만으로
연결하므로 254행은 이미 추적됩니다(§1-1). 실제 요청 대상은 나머지 중 앱 계층 **390행**입니다.

## 3. 기대 효과 — 파이프라인 전/후 실측

> **⚠ 2026-07-31 정정.** 이 절의 초판은 SDS 엔트리 통계만으로 "요구당 함수 94 → 25,
> 도달 요구 46 → 51" 이라 적었습니다. **둘 다 틀렸습니다.** 추적성 파이프라인을 실제로
> 전/후 두 번 돌려 재측정한 값으로 교체합니다. 아래가 정확한 값입니다.

SRS·SDS·UDS 원문을 넣고 추적성 매트릭스를 **병기 전 / 병기 후** 두 번 생성해 대조했습니다.

| 축 | 병기 전(현행) | **앱 390행 병기(요청안)** | (참고) 646행 전량 |
|---|---|---|---|
| **추적되는 UDS 함수** | **385 / 1,026 (37.5%)** | **765 / 1,026 (74.6%)** ✅ | 862 (84.0%) |
| UDS 링크를 가진 요구 | 64 / 68 | **64 / 68 (변화 없음)** | 64 / 68 |
| 요구당 함수 (중앙 · 최대) | 23 · 201 | 26 · 445 ⚠ | 26 · 497 |
| 총 링크 수 | 3,212 | 3,610 | 3,711 |
| 행 ASIL | — | **완전 일치(불변)** | 불변 |
| 인프라에 붙는 거짓 추적 | — | **0** ✅ | 256행 ❌ |

**핵심 이득은 하나입니다 — 추적되는 함수가 385 → 765 로 약 2배(+380개)** 늘어납니다.
"이 함수는 어느 요구를 구현하는가"에 답할 수 있는 함수가 37.5% → 74.6% 가 됩니다.

인프라 256행까지 넣으면 +477(84.0%)이 되지만, 그 차이는 **부트로더 flash 루틴과 SPI
드라이버에 앱 기능ID를 붙여서 얻는 숫자**입니다. 감사에서 되레 문제가 되므로 뺐습니다.

### ⚠ 다만 연결 입도(fan-out)는 **좋아지지 않고 나빠집니다**

초판의 "3.8배 정밀화"는 오류였습니다. 이유:

- SwFn 자체의 폭은 확실히 좁습니다(요구 중앙 **1**, 최대 6 / SwCom 은 5, 17) — 이 부분은 맞습니다.
- 그러나 매트릭스의 fan-out 은 **폭이 아니라 "함수 쏠림 × 폭"** 으로 정해집니다.
- SwCom 단독 900행은 31개 SwCom 에 **중앙 11개, 최대 175개**로 몰려 있습니다.
  한 SwCom 에 몰린 함수를 SwFn 하나로 보내면 **그 SwFn 의 요구가 그 함수들을 통째로 받습니다.**
- 실측: `SwTR_0102` 한 요구가 **189 → 497개** 함수를 받게 됩니다.

**fan-out 결과는 배정 정밀도에 전적으로 달려 있습니다:**

| 배정 방식 | 요구당 함수(중앙) | 총 링크 |
|---|---|---|
| 함수마다 **정확히 1개** SwFn 지정 | 26 | 3,711 |
| 후보 SwFn 을 **여러 개 나열** | **74** ❌ | **10,203** (3.2배) |

⟹ **"관련 있어 보이는 SwFn 을 여러 개 적는 것"은 하지 말아 주십시오.** 그러면 추적
변별력이 오히려 지금보다 나빠집니다. 함수 하나에 SwFn 하나가 원칙입니다.

### 부록 A 의 'SwFn 후보' 열이 어디까지 도와주는지 (정직 고지)

부록 A 에는 **SwCom 의 요구집합과 겹치는 SwFn 후보**를 미리 나열해 두었습니다. 추정값이
아니라 선택지를 좁힌 것입니다. 다만 **모든 행에서 좁혀지지는 않습니다:**

| 후보 수 | 행 수 | 의미 |
|---|---|---|
| 0개 | 6 | 겹치는 SwFn 없음 — 검토 필요 |
| 1~6개 | **103** | ✅ 실질적으로 좁혀짐 |
| 7개 이상 | **281** | ❌ 좁히지 못함 — 비고에 명시했습니다 |

SwCom 이 요구를 많이 가질수록 교집합이 커져 후보가 SwFn 목록 전체에 가까워지기 때문입니다.
**후보가 7개 이상인 행은 목록을 참고만 하시고 설계 판단으로 정해 주십시오** — 앞의 것을
그냥 고르시면 근거 없는 매핑이 됩니다.

더 나은 단서를 찾아봤으나 문서에 없었습니다. SwFn 설명문에 UDS 함수명이 적힌 경우는
**0 / 390**, 설명 단어와 함수명 토큰이 겹치는 경우도 355 / 390(91%)이 무매칭이었습니다.

또한 **공용 산술·유틸 25건**(`u32s_Add_Guarded`·`ClampTemperature` 등)은 여러 기능이 함께
쓰므로 단일 SwFn 배정이 부적절할 수 있습니다. 부록 A 비고에 표시해 두었습니다.

### SwCom_35(Bootloader)는 제외가 맞습니다 — 175개 함수

초판은 "Bootloader 영역에 SwFn 을 신설할지 정해 달라"고 적었으나, **제외가 맞습니다.**

SwCom_35 소속 175행을 계층별로 보면 **140행이 부트로더·재프로그래밍**(`EraseFlashSector`·
`FTMRZ_Prog_Phrase` 등), 23행이 기본 드라이버, 2행이 라이브러리입니다. 이 영역은 앱 기능
설계(SwFn)의 대상이 아니며, SwCom_35 가 참조하는 요구도 `SwTR_0106` 하나뿐입니다.
해당 행은 부록 D 에 근거와 함께 실었습니다.

## 4. ⚠ 제약 — SwCom 을 지우면 안 됩니다

| 축 | SwFn | SwCom |
|---|---|---|
| **ASIL 표기 보유** | **0 / 41** ❌ | **33 / 33** ✅ |

SDS 원문에서 SwFn 엔트리에는 ASIL 이 **하나도 기재되어 있지 않습니다.** 도구는 요구사항별
ASIL 을 SDS 컴포넌트에서 끌어올려(roll-up) 계산하므로, SwCom 을 SwFn 으로 **교체**하면
안전등급 근거가 사라집니다.

따라서 기재 형식은 **병기**입니다:

```
현재 :  SwCom_14
요청 :  SwCom_14, SwFn_10
```

## 5. 한계 — 이 조치로 해결되지 **않는** 것 (정직 고지)

| 질문 | 답 |
|---|---|
| 미추적 함수의 역추적 링크가 생기나 | **예** — 추적 함수 385 → 765 (+380) |
| 연결 입도(fan-out)가 좋아지나 | **아니오, 나빠집니다** — 요구당 23 → 26(정확 배정) / 74(다중 나열). §3 정정 참조 |
| 요구사항 커버리지가 올라가나 | **아니오** — 이미 **68 / 68 = 100%** 입니다 |
| 추적되는 **요구** 수가 느나 | **아니오** — UDS 링크 보유 요구 64 / 68 로 **불변**입니다 |
| **함수 단위** 정밀 추적이 되나 | **아니오** — SwFn 41개에 390행이라 그룹 단위 roll-up 입니다 |
| ASIL 정합이 좋아지나 | **아니오** — 행 ASIL 은 SDS 컴포넌트 롤업 기준이라 **완전히 불변**입니다(실측 확인) |

**남은 4건은 병기해도 안 닿습니다** — `SwNTR_0201` · `SwNTR_0203` · `SwNTSR_0101` ·
`SwNTSR_0102`. 전부 비기능·안전 요구(SwNTR/SwNTSR)이고 SwDS 어느 엔트리도 참조하지
않습니다. 이 계층은 설계를 거치지 않고 **시험으로 직접 검증**하는 구조라 정상입니다.

**함수 단위 추적**을 하려면 소스 주석(`@related SwTR_0101` 형태)이 필요한데 현재 **0건**입니다.
다만 이 프로젝트의 실측 ASIL 분포는 **A 62 / QM 2 / 미상 4** 이므로, ASIL A 수준에서는
SwFn 병기로 실무상 충분하다고 판단합니다. ASIL C/D 항목이 생기면 그때 소스 주석이 필요합니다.

> **최종 확정은 설계 판단입니다.** 부록 A 의 SwFn 후보 열은 선택지를 좁혀 드린 것이지
> 도구의 추정값이 아닙니다. **'팀 확정' 열에 직접 적어** 주십시오.

## 7. 부록 C — 별건 확인 요청 (문서–코드 드리프트)

SwDS 에 설계로 기재돼 있으나 SwUDS 에는 없는 함수가 **241건**입니다. 소스(`NE1AW_PORTING`,

## 8. 요약

| 요청 | 대상 | 성격 |
|---|---|---|
| **주** UDS `Related ID` 에 SwFn 병기 (SwCom 유지, **함수당 1개**) | **390행**(부록 A) | 추적 함수 385 → 765 (약 2배) |
| **부** 부록 D 계층 분류에 오분류가 있는지 확인 | 256행 | 자동 분류라 되돌릴 수 있음 |
| **부** 코드 비활성화 함수의 SwDS 잔존 정리 | 12건 | 문서–코드 정합 |
| **부** UDS 누락 후보 확인 | 6건 (그중 4건은 외부 라이브러리 가능) | 문서 완전성 |

**정직하게 정리하면** — 이 조치가 주는 것은 **"함수 → 요구" 방향의 추적률**(37.5% → 74.6%)
하나입니다. 요구 커버리지(이미 100%)·ASIL·"요구 → 함수" 변별력은 오르지 않으며, 마지막
항목은 배정이 거칠면 **오히려 나빠집니다**(§3).

작업량도 정직하게 적으면, 390행 중 후보가 실제로 좁혀진 건 **103행**이고 나머지 **281행은
설계 판단**이 필요합니다(§3). 상위 3개 SwCom 이 78%라 컴포넌트 단위로 나눠 진행하실 수 있습니다.

따라서 **긴급하지 않습니다.** 감사(audit)에서 "이 함수가 무슨 요구를 구현하는지" 를 물을
가능성에 대비하는 성격이며, 그 시점에 맞춰 진행하시면 됩니다. 착수하신다면 §3의
"함수 하나에 SwFn 하나" 원칙만은 지켜 주시기 바랍니다.
