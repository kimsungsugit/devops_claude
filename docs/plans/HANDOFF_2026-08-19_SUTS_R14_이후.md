### R17 `tl_pdu[N*8]` — **종결 확정** (인계본의 "다음 단계" 를 실행한 결과)

R14 인계본은 "선언을 소스에서 직접 확인하는 게 다음 단계" 로 멈췄다. 찾았다:

```c
typedef l_u8 lin_tl_pdu_data[8];   // lin.h:179   ← 둘째 차원 8 은 여기서
lin_tl_pdu_data  *tl_pdu;          // lin.h:559   ← **포인터**. 첫 차원은 런타임 할당
#define MAX_QUEUE_SIZE 7           // lin_cfg.h   ← 정본의 `7`
```

정본 표기 55칸 = `[7*8]` 33 · `[1*8]` 7 · `[4*8]` 1 · base 3 · `[i][j]` 11.
`[N*8]` 41칸의 N 은 **실행 시 할당된 행 수**라 정적 유도 불가다. 게다가 `lin.h` 는

`[i][j]` 리터럴 11칸만 소스 본문에서 유도 가능하나, 그러려면 아래 파서 비대칭을

## 알려진 파서 결함 — **고치면 나빠진다** (지우지 말 것)

`report_gen/function_analyzer.py:_scan_name_usage` 에 비대칭이 있다:

```python
# 멤버 경로는 체인을 끝까지 문다
for m in re.finditer(rf"\b{name}\b({_MEMBER_CHAIN_RE})", line):   # RespMsg->data     ✓
    u["members"].add(...)
# 그런데 첨자는 name 바로 뒤 `[` 만 잡는다
for m in re.finditer(rf"\b{name}\b\s*\[\s*([^\]]+)\s*\]", line):  # RespMsg->data[0]  ✗
    u["indexes"].add(...)
```

`hash[i]`·`Values[1]` 처럼 **이름 직후** 첨자는 잡히고(산출물에 `(idx:)` 140 슬롯),
`RespMsg->data[0]` 처럼 **멤버 경로 뒤** 첨자는 통째로 누락된다.

**누가 봐도 버그다. 그런데 고치면 정본과 멀어진다** — 얻는 슬롯 76개(리터럴 39 ·
변수식 37) 중 정본 적중은 3칸이고 44칸이 과잉이다(R20). 게다가 소비처
(`generators/suts.py`)는 `(idx:)` 를 확장에 **안 쓴다**(R10 이 관찰 첨자를 기각한 결과,
`_PARAM_ANNOT_KEYS` 로 벗겨내기만 한다). 즉 파서만 고치면 **산출물이 안 변한다**
= 관측 불가한 변경이다.

→ **손대지 않는다.** 다른 축에서 멤버 경로 첨자가 꼭 필요해지면 그때 이 항목부터 읽을 것.

## R24 가 **닫은** 축 — 인계본의 다음 후보가 둘 다 기각됐다

### ① `EepIsCommandBusy() return` 5칸 — 매크로 가설은 **틀렸다**

인계본은 "`calls_list` 생산자가 매크로 안의 호출을 못 본다" 로 적고 "다음 라운드의
첫 삽" 이라 했다. 재보니 아니다:

    미달 `X() return` 12칸 중 10칸: 그 피호출이 unit 의 **본문 0회 · 파일 전체 0회**

본문 스캔으로 `calls_list` 를 보강하는 규칙은 **생산 5 · 적중 0**. 원인은 따로 있다:

    EEPROM_GetByte 등 5 unit   → NE1AW_PORTING\Generated_Code\EEPROM.c   (**APP**)
    EepIsCommandBusy 등 4 함수 → PDS128_FBL\Sources\Eeprom\EEPROM.c      (**FBL**)

**서로 다른 서브프로젝트다.** APP 의 `EEPROM_GetByte` 는 그 이름을 부르지 않는다.
정본이 시험한 건 FBL 쪽 흐름이다 — 우리 소스에서 정적으로 유도할 근거가 없다.
(unit 자체가 빠진 건 아니다: 정본 unit 1,005개 **전부** 우리 산출물에 있다.)

### ② 레지스터 별칭 `r_FSTAT.Byte` 34칸 — 전역 치환은 **-300**

정본은 두 표기를 **다 쓴다**: `_X` 258칸 · `r_X` 170칸. 선언 위치가 갈린다 —
`_FSTAT` 는 APP(`Generated_Code\Vectors.c`), `r_FSTAT` 는 FBL(`mc9s12zvl64.h`).
FBL 소스는 매크로를 쓰고 FBL 헤더가 그걸 편다:

    EEPROM.c(FBL):  if ((byte)FSTAT_CCIF == (byte)0U)
    헤더(FBL):       #define FSTAT_CCIF   r_FSTAT.Bits.CCIF

손익을 양방향으로 쟀다:

    전역 치환 `_X`→`r_X`        얻음  23 · **잃음 323**  → 기각
    FBL unit 에서만 치환         얻음   2 · 잃음   0  · 짝 치환 정밀도 **10.0%**

⚠ **R22 의 `[0]` 함정과 같은 형태다.** 한쪽 방향만 재면 "정본이 `r_` 로 적는다" 만
보이고 4,895칸 손실을 못 본다. 표기 축은 **반드시 양방향**으로 잰다.

⚠ "교차 서브프로젝트 이름 누수" 로 일반화하려다 **자기 반증**했다: 같은 검사로
정본을 재니 정본의 누수가 **60칸**(우리 32)이고 우리 32 중 17 은 정본과 **일치**
한다. 선언 스캔이 거친 것이라(로컬 `data`·`ptr` 이 섞인다) 결함으로 보고할 근거가
안 된다 — **대조군을 안 돌렸으면 없는 결함을 보고할 뻔했다**.

## R25 — **값 축**. 24라운드가 전부 이름 축이었다는 걸 이제야 쟀다

R24 인계본은 "정본 대조로 더 얻을 것은 사실상 없다" 로 닫았다. **그건 이름 축에
한해서만 참이었다.** 이 시리즈의 대조 단위는 줄곧 `(unit, 변수이름)` 이었고,
그 칸에 **어떤 값이 들어가는지**는 한 번도 안 쟀다.

### 정본 값 레이아웃 (시트 `2.SW Unit Test Spec`, 실측)

    행4  헤더    ... 8:(seq#) 9~103:Inpt[0..95] 104~187:ExpR[0..83]
    행5  이름 행  4:unit명 · 9+ 변수 이름            ← unit 블록 시작
    행6~ 값 행    8:seq번호 · 9+ 값                  ← 시퀀스 하나당 한 행

    블록 1,014개 · 고유 unit 1,005 · 시퀀스 6,886행 · 블록당 평균 6.79

⚠ **블록은 unit 당 1개가 아니다.** 같은 함수 이름의 블록이 2개인 unit 이 **9종**
있다(`main`·`EEPROM_GetByte`·`LINPHY0_Init` …) — R24 가 찾은 APP/FBL 교차
서브프로젝트다. dict 로 덮어쓰면 이름 **16/25칸 · 시퀀스 66행**이 조용히 사라진다
(실제로 첫 판이 그랬다). 파서 무결성은 **이름 합집합이 기존 지형과 정확히
6,014 / 5,389 로 일치**하는지로 검증한다(차집합 0).

### ▶ 값 축 첫 수치

|  | 정본 값 인스턴스 | 우리가 낸 것 | **재현율** |
|---|---|---|---|
| 입력 | 37,059 | 21,416 | **57.8%** |
| 기대 | 14,994 | 9,130 | **60.9%** |

이름 축(91.2% / 92.4%)과 **30%p 넘게 벌어진다.** 이게 지금 SUTS 의 가장 큰 미측정
결손이었다.

### ⚠ 내 가설이 뒤집혔다 — 시퀀스는 더 내는데 값은 더 좁다

우리는 시퀀스를 **더** 낸다(평균 9.51 vs 6.79 · 806 unit 에서 우리가 더 많다).
그래서 "우리 값 집합이 상위집합이라 완전일치가 0 인 것" 이라 봤다. 실측은 반대다:

    B 우리 ⊂ 정본 (우리가 좁다)   62.2%
    C 교차                        32.1%
    D 무교집합                     5.5%
    A 정본 ⊆ 우리 (우리가 넓다)     0.2%

우리 전략은 **한 시퀀스에서 전 입력을 같은 경계로** 몰아넣는다(`BV_MIN_INV` → 전부 -1).
정본은 시퀀스마다 값을 바꾼다. 그래서 행은 많은데 칸당 값 가짓수가 적다.

### 못 낸 값 전수 귀속

| 입력 15,643 | | 기대 5,864 | |
|---|---|---|---|
| **L 절단 사다리(상한 초과)** | **50.3%** | **W 절단 결과** | **47.3%** |
| R 범위 내 다른 값 | 31.5% | R 범위 내 다른 값 | 35.8% |
| U 하한 미만 | 12.6% | S 비수치(enum) | 9.6% |
| S 비수치 | 5.6% | L 절단 사다리 | 6.2% |

**정본은 타입 폭 절단(truncation)을 시험한다.** U8 사다리 원본 육안 확인:

    seq  1     2      3      4     5       6           7
    Inpt 0x0   0x7F   0xFF   -1    0x100   0x140       0x1FF
    ExpR 0x0   0x7F   0xFF   0xFF  0x0     0x40(=64)   0xFF

`0x140`(320) 은 절단하면 `0x40`(64) 이라 **다른 시퀀스가 안 만드는 관측치**를 낸다.
못 낸 값 1·2위가 320(2,418회)·511(2,274회)이고 기대 열 1위가 64(1,879회)인 게
같은 규칙의 앞뒤였다.

### ✅ R25 채택 — `uint32_t` 의 `mid` 는 오타였다

    "uint32_t": {... "mid": 2**15 ...}     ← 32768. uint32 중앙도 uint16 중앙도 아니다

세 갈래가 같은 답을 가리킨다:

1. **내부 규칙** — 부호 없는 mid 는 `max // 2` (255//2=127 · 65535//2=32767)
2. **형제 생성기** — `generators/sits.py:_BOUNDARY_SETS["uint32"][3]` 이 **이미
   `0x7FFFFFFF`** 였다. uint8·uint16·int16 은 두 생성기가 일치했고 **uint32 만** 갈렸다
3. **정본 실측** — 정본은 uint32 칸에 `0x7FFFFFFF` 를 쓰고 우리가 못 내던 칸이 52개.
   반대로 **우리가 쓰던 32768 은 정본 uint32 칸에 0회** — 아무도 안 보는 값을 시험했다

라이브: 입력 57.6→**57.8%** · 기대 60.8→**60.9%** · 과다 −52/−8 로 **정확히 맞바뀜**
(사라진 맞춤 0). 쓸모없던 값이 맞는 값으로 치환됐다.

⚠ **이건 이미 발견돼 있던 것이다.** `tests/unit/test_c_type_bounds_mirror.py` 가
"uint32 중앙이 아니지만 **실 문서 산출값이라 여기서 고치지 않는다 — 별도 판단 필요**"
로 남겨 뒀다. R25 가 그 **별도 판단**을 수치로 공급했다. 그 docstring 도 갱신했다
(안 고치면 저장소가 스스로에 대해 거짓을 적어 둔 채로 남는다).

### 결함 아님이 확인된 것 — 랩어라운드 기대값

의심했다: U8 에 `256`(max_inv)을 넣고 기대 열에 `256` 이라고 적으면 그건 커버리지
부족이 아니라 **성립하지 않는 시험**이다. 실측은 깨끗하다:

    우리가 max_inv 입력을 내는 칸 2,531개 → **2,531개 전부 기대가 절단값**
    절단 안 된 원값을 기대에 쓴 칸 **0개**

### ⚠ 사다리 확장은 **결함 수정이 아니라 범위 결정**이라 안 했다

| 후보 | 적중 | 과다 | 정밀도 |
|---|---|---|---|
| `max_inv*1.25` (U8:320) | 2,419 | 3,035 | **44.4%** |
| `max_inv + 0xFF` (U8:511 · U16:65791) | 2,406 | 3,076 | **43.9%** |
| `max_inv + max` (U8:511) | 2,329 | 3,153 | 42.5% |
| `min_inv - 9` (U8:-10) | 844 | 4,638 | 15.4% ⛔ |

앞 셋은 R23(34.3% 채택)·R24(50.0% 채택) 기준선 근처다. **그런데 채택하지 않았다**:

- `1.25배`·`+0xFF` 둘 다 **타입에서 유도되지 않는다**. U8 은 `+0x40`, U16 은 `+0x400`

- 이건 결손 보정이 아니라 **시험 케이스를 늘리는 결정**이다. 우리는 이미 시퀀스를

- ⚠ 반대 방향(범위 축소)이 자율 금지인 것과 대칭으로, 확대도 자율로 하지 않는다
