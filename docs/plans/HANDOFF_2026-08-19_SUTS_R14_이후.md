### R19 방향 판정 축 — **기각**

`s_sha256_final(SHA256_CTX *ctx, __far U8 *hash)` 에서 정본은 `hash` 를 기대 열
32칸으로 적는데 우리는 입력 열에만 냈다. "out 파라미터를 기대 열에 안 넣는다"는
결함처럼 보였다. 전수로 재니 **정반대**였다:

    대상 89 이름족의 파서 태그:  [IN] 79 (89%) · 파서에 없음 6 · [INOUT] 2 · [OUT] 1(+1)

    규칙 후보                     적중   과다   정밀도
    outputs 의 [OUT]                2     13    13.3%
    outputs 의 [OUT]+[INOUT]        4     84     4.5%
    전체 슬롯 [OUT]+[INOUT]         4    423     0.9%
    전체 [INDIRECT*]                0  2,446     0.0%

즉 정본이 기대 열에 넣은 건 파서가 `[IN]` 으로 **정확히** 판정한 것들이다. 정적
유도로 재현할 축이 아니다(VectorCAST 가 입력값을 양쪽에 기록한 것).

곁가지 확인: SwUDS 우선 정책이 소스의 `[OUT]` 을 덮어써 버리는 건 **사실**이다
(89칸). 그런데 그중 정본이 원하는 건 4칸이고, 나머지는 이미 종결 선언된
`SafeWriteQueue 중간마디` 축이다. **뚫을 값이 없다.**

출처 판정(전수): 정본↔SwUDS 불일치 119 · 소스추론 유래 47 ·
**"우리가 문서를 안 따랐다" 0칸**. SwUDS 는 우리 편이다.

### R17 `tl_pdu[N*8]` — **종결 확정** (인계본의 "다음 단계" 를 실행한 결과)

R14 인계본은 "선언을 소스에서 직접 확인하는 게 다음 단계" 로 멈췄다. 찾았다:

```c
typedef l_u8 lin_tl_pdu_data[8];   // lin.h:179   ← 둘째 차원 8 은 여기서
lin_tl_pdu_data  *tl_pdu;          // lin.h:559   ← **포인터**. 첫 차원은 런타임 할당
#define MAX_QUEUE_SIZE 7           // lin_cfg.h   ← 정본의 `7`
```

정본 표기 55칸 = `[7*8]` 33 · `[1*8]` 7 · `[4*8]` 1 · base 3 · `[i][j]` 11.
`[N*8]` 41칸의 N 은 **실행 시 할당된 행 수**라 정적 유도 불가다. 게다가 `lin.h` 는
`verify=X` 파일이라 파서가 안 읽는다 — **11차의 `g_LinIntCtrl.dataBuffer` 와 같은 벽**
(인계본의 예견이 맞았다). verify 필터를 풀어도 `[8]` 만 얻고 `7` 은 못 얻는다.

`[i][j]` 리터럴 11칸만 소스 본문에서 유도 가능하나, 그러려면 아래 파서 비대칭을
고쳐야 하고 그건 44칸 과잉을 동반한다(R20). **값이 안 맞는다.**

## 알려진 파서 결함 — **고치면 나빠진다** (지우지 말 것)

`report_gen/function_analyzer.py:_scan_name_usage` 에 비대칭이 있다:

```python
# 멤버 경로는 체인을 끝까지 문다
for m in re.finditer(rf"\b{name}\b({_MEMBER_CHAIN_RE})", line):   # RespMsg->data     ✓
    u["members"].add(...)
# 그런데 첨자는 name 바로 뒤 `[` 만 잡는다
for m in re.finditer(rf"\b{name}\b\s*\[\s*([^\]]+)\s*\]", line):  # RespMsg->data[0]  ✗
    u["indexes"].add(...)
```

`hash[i]`·`Values[1]` 처럼 **이름 직후** 첨자는 잡히고(산출물에 `(idx:)` 140 슬롯),
`RespMsg->data[0]` 처럼 **멤버 경로 뒤** 첨자는 통째로 누락된다.

**누가 봐도 버그다. 그런데 고치면 정본과 멀어진다** — 얻는 슬롯 76개(리터럴 39 ·
변수식 37) 중 정본 적중은 3칸이고 44칸이 과잉이다(R20). 게다가 소비처
(`generators/suts.py`)는 `(idx:)` 를 확장에 **안 쓴다**(R10 이 관찰 첨자를 기각한 결과,
`_PARAM_ANNOT_KEYS` 로 벗겨내기만 한다). 즉 파서만 고치면 **산출물이 안 변한다**
= 관측 불가한 변경이다.

→ **손대지 않는다.** 다른 축에서 멤버 경로 첨자가 꼭 필요해지면 그때 이 항목부터 읽을 것.

| `u8char` · `Addr` 등 롱테일 | 118 | ⛔ 포인터인데 `(idx:)` 조차 없다 |

### ⚠ `struct_member_arrays` 에 답이 있는 것처럼 보이지만 아니다

`SHA256_CTX -> {'state': '[8]', 'buffer': '[64]'}` 가 **파서 산출물에 실제로 들어 있다**.
그래서 "조회 경로만 이으면 `ctx.state` 24칸이 열린다" 로 보이는데, `_struct_member_dims`
가 포인터 파라미터를 **일부러** 제외하고 있다(R20: 일치 +34 에 과다 **+176**).
정본은 `ctx.buffer` 를 선언 64칸이 아니라 **9칸**(`[0]`, `[56..63]`)만 적는다 — 실행
관측이라 선언 크기와 무관하다. **이 8개짜리 맵을 보고 다시 열지 말 것.**

### `Values` 9칸 — `[OUT]→입력` 은 여전히 손실 1

`[OUT]` + 리터럴 `(idx:)` 슬롯은 저장소 전체에 **7개**뿐이고 R21 이 이미 소진했다.
남은 `Values` 를 위해 "이름이 `inputs` 키에도 있을 때만" 이라는 새 조건을 시험했는데
**`Values` 와 `versionOut` 이 둘 다 걸려 못 가른다**:

    (A) 조건 없이           적중 10 · 손실 1 · 과다 43
    (B) inputs 동시등장     적중  9 · 손실 1 · 과다  4   ← 손실 0 아님 → 기각

### R22 의 자기 정정

`(idx:)` 슬롯 401개를 관문별로 분류하면서 `[INOUT]` 이 **124칸**을 놓치는 것처럼
쟀는데, 그건 실제 생성물과 대조하지 않은 **상한**이었다. 라이브로 다시 재니
`[INOUT]→양쪽` 은 적중 81 그대로(증가 0) · 과다만 18→34. **R21 판정이 정확했다.**
*"새 측정이 기존과 다르면 새 측정부터 의심하라"* 가 또 맞았다.

## ✅ R23 채택 — stub **출력 파라미터** (과다를 재다가 나온 미달 축)

과다를 분해하는 과정에서 *정본에만 있는 표기*가 걸렸다. 우리가 못 내는 게 아니라
**낼 생각을 안 한** 칸이었다:

    정본 Inpt:  EEPROM_GetByte() Data[0]   sf_TryAddU32() sum[0]
                sf_LinDataPolling() e_Err[0]   EepSetupFCCOB() pIndex[0]

VectorCAST 가 피호출을 stub 하면 반환값만 주입되는 게 아니다. 포인터 **출력
파라미터에 써 넣을 값**도 시험자가 정해야 한다. `_stub_return_names` 가 연 축의
나머지 절반이다.

    입력 5,459 (90.8%) → **5,471 (91.0%)**   과다 1,451 → 1,474 (+23)
    기대 4,980 (92.4%) → 4,980 (변화 없음)
    **사라진 맞춤 0 · 사라진 칸 0** (라이브 재생성 · 집합 뺄셈)

### 비-void 조인이 이 축의 전부다

    후보 규칙                     생산   적중   과다   정밀도
      조건 없음([OUT] 전부)        154     12    142     7.8%
      **비-void 피호출만**          35     12     23    34.3%   ← 채택
      out-param 1개뿐               43      9     34    20.9%
      비-void ∧ 1개뿐               28      9     19    32.1%

**같은 적중 12 를 과다 142→23 으로 낸다.** 우연이 아니다 — 비-void 집합은 우리가
이미 `X() return` 을 내는 대상과 정확히 같고, **stub 되는 함수만** 그 출력 파라미터를
주입받는다. 근거가 같으므로 두 경로가 같은 조인을 쓴다.

### ⚠ 접미 `[0]` 은 R22 를 뒤집는 게 **아니다**

R22 가 기각한 건 *배열 변수*에 `[0]` 을 붙이는 것이다(정본의 지배 표기가 base 라

두 표기를 다 쟀다 — `[0]` 적중 12 · **접미 없음 적중 0**. 이름족이 다르면 표기도 다르다.

### 입력 열 전용 — 기대 열은 낼 수 없다
