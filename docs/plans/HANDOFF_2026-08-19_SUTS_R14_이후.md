## ⚠ 다시 파지 말 것 (근거와 숫자)

### R19 방향 판정 축 — **기각**

`s_sha256_final(SHA256_CTX *ctx, __far U8 *hash)` 에서 정본은 `hash` 를 기대 열
32칸으로 적는데 우리는 입력 열에만 냈다. "out 파라미터를 기대 열에 안 넣는다"는
결함처럼 보였다. 전수로 재니 **정반대**였다:

    대상 89 이름족의 파서 태그:  [IN] 79 (89%) · 파서에 없음 6 · [INOUT] 2 · [OUT] 1(+1)

    규칙 후보                     적중   과다   정밀도
    outputs 의 [OUT]                2     13    13.3%
    outputs 의 [OUT]+[INOUT]        4     84     4.5%
    전체 슬롯 [OUT]+[INOUT]         4    423     0.9%
    전체 [INDIRECT*]                0  2,446     0.0%

즉 정본이 기대 열에 넣은 건 파서가 `[IN]` 으로 **정확히** 판정한 것들이다. 정적
유도로 재현할 축이 아니다(VectorCAST 가 입력값을 양쪽에 기록한 것).

곁가지 확인: SwUDS 우선 정책이 소스의 `[OUT]` 을 덮어써 버리는 건 **사실**이다
(89칸). 그런데 그중 정본이 원하는 건 4칸이고, 나머지는 이미 종결 선언된
`SafeWriteQueue 중간마디` 축이다. **뚫을 값이 없다.**

출처 판정(전수): 정본↔SwUDS 불일치 119 · 소스추론 유래 47 ·
**"우리가 문서를 안 따랐다" 0칸**. SwUDS 는 우리 편이다.

### R20 포인터 버퍼 입도 정합 — **기각**

사용자 결정(이름은 우리 것 유지, 입도만 정본과 맞춤)에 따라 쟀다. 새로 나는 111칸:

    63 (56.8%)  VECTORCAST 자리 — 이름 결정상 지표엔 안 잡히나 입도는 정본과 동일
    44 (39.6%)  정본은 같은 이름을 **다른 입도**로 적음 → **과잉**
     3 ( 2.7%)  적중 (`FTMRZ_Prog_Phrase::PS.Add.ByteArray[1..3]`)
     1 ( 0.9%)  정본이 그 이름을 아예 안 적음

정본은 `RespMsg.data` 를 **1칸**으로 적는데(입력 열, 포인터 값) 새 규칙은 3~4칸으로
펼친다. 반대로 `ctx.state` 는 정본도 8칸이다. **둘을 구분할 신호가 없다** — 양쪽 다
"포인터 파라미터의 멤버". R16 기각(폭 좁히기)과 대칭인 형태다.

⚠ 열 상한 96칸이 있어 과잉 확장은 **뒤 변수를 밀어낸다**(캡 규약).
⚠ 사용자에게 제시한 선택지에 "시험 칸수는 정본과 동일해짐" 이라고 적었는데
   **56.8% 만 그렇다**. 선택지를 만들 때 그 분해를 먼저 쟀어야 했다.

### R17 `tl_pdu[N*8]` — **종결 확정** (인계본의 "다음 단계" 를 실행한 결과)

R14 인계본은 "선언을 소스에서 직접 확인하는 게 다음 단계" 로 멈췄다. 찾았다:

```c
typedef l_u8 lin_tl_pdu_data[8];   // lin.h:179   ← 둘째 차원 8 은 여기서
lin_tl_pdu_data  *tl_pdu;          // lin.h:559   ← **포인터**. 첫 차원은 런타임 할당
#define MAX_QUEUE_SIZE 7           // lin_cfg.h   ← 정본의 `7`
```

정본 표기 55칸 = `[7*8]` 33 · `[1*8]` 7 · `[4*8]` 1 · base 3 · `[i][j]` 11.
`[N*8]` 41칸의 N 은 **실행 시 할당된 행 수**라 정적 유도 불가다. 게다가 `lin.h` 는
`verify=X` 파일이라 파서가 안 읽는다 — **11차의 `g_LinIntCtrl.dataBuffer` 와 같은 벽**
(인계본의 예견이 맞았다). verify 필터를 풀어도 `[8]` 만 얻고 `7` 은 못 얻는다.

`[i][j]` 리터럴 11칸만 소스 본문에서 유도 가능하나, 그러려면 아래 파서 비대칭을
고쳐야 하고 그건 44칸 과잉을 동반한다(R20). **값이 안 맞는다.**

## 알려진 파서 결함 — **고치면 나빠진다** (지우지 말 것)

`report_gen/function_analyzer.py:_scan_name_usage` 에 비대칭이 있다:

```python
# 멤버 경로는 체인을 끝까지 문다
for m in re.finditer(rf"\b{name}\b({_MEMBER_CHAIN_RE})", line):   # RespMsg->data     ✓
    u["members"].add(...)
# 그런데 첨자는 name 바로 뒤 `[` 만 잡는다
for m in re.finditer(rf"\b{name}\b\s*\[\s*([^\]]+)\s*\]", line):  # RespMsg->data[0]  ✗
    u["indexes"].add(...)
```

`hash[i]`·`Values[1]` 처럼 **이름 직후** 첨자는 잡히고(산출물에 `(idx:)` 140 슬롯),
`RespMsg->data[0]` 처럼 **멤버 경로 뒤** 첨자는 통째로 누락된다.

**누가 봐도 버그다. 그런데 고치면 정본과 멀어진다** — 얻는 슬롯 76개(리터럴 39 ·
변수식 37) 중 정본 적중은 3칸이고 44칸이 과잉이다(R20). 게다가 소비처
(`generators/suts.py`)는 `(idx:)` 를 확장에 **안 쓴다**(R10 이 관찰 첨자를 기각한 결과,
`_PARAM_ANNOT_KEYS` 로 벗겨내기만 한다). 즉 파서만 고치면 **산출물이 안 변한다**
= 관측 불가한 변경이다.

→ **손대지 않는다.** 다른 축에서 멤버 경로 첨자가 꼭 필요해지면 그때 이 항목부터 읽을 것.
