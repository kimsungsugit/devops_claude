ARIA · ISO 26262 SW DOCUMENT AUTOMATION

문서 자동화는 완성본을 대신하는 것이 아니라, 검토 가능한 초안의 출발점을 높인다

각 문서가 요구하는 권위 입력과 Revision을 고정한 뒤, 결정론 분석으로 사실·수치·링크를 만들고 LLM은 근거가 있는 설명만 보강한다. 최종 산출물은 자동 생성된 검토 초안이며, 승인과 시험 적합성 판단은 사람이 확정한다.

01 · Operating principle

자동화의 핵심은 ‘사실 생성’과 ‘문장 생성’을 분리하는 것이다

코드가 구조와 관계를 반복 가능하게 계산하고, AI는 그 결과를 읽기 쉬운 문장으로 정리한다. 이 경계를 지켜야 산출물의 장점은 살리고 ISO 26262 증거의 과대평가는 막을 수 있다.

1

결정론 코어

요구 ID, 함수, 호출관계, 입출력, 시험 매핑, P/F와 커버리지를 코드로 계산한다. 같은 입력은 같은 결과를 만든다.

2

근거 제한형 LLM

결정론 결과, 승인 문서, RAG excerpt 안에서 설명과 초안을 보강한다. 근거가 없으면 N/A 또는 검토 대상으로 남긴다.

3

사람 승인 게이트

요구 의도, ASIL, expected result, stub 조건, deviation 수용, 최종 evidence 채택은 책임자가 확정한다.

BASELINE SRS · SDS · HSIS 승인 요구·설계·인터페이스
ANALYZE Source / AST 함수·분기·호출·전역변수
DRAFT UDS · STS · SUTS · SITS 설계·시험명세 검토 초안
EXECUTE VectorCAST Unit / Integration 실행 증거
ASSETIZE Reports · Trace · RAG 보고·영향분석·재사용
중요: UDS·SUTS·SITS 초안은 소스만으로도 시작할 수 있지만, STS와 요구사항 종단 추적성은 승인된 SRS/SwRS 없이는 완성할 수 없다. RAG는 누락된 요구사항을 대신 만들지 않고 후보 연결과 과거 근거를 제안한다.

02 · Authoritative inputs

입력 기준문서는 자동화의 재료이자 넘지 말아야 할 권위 경계다

SRS·SDS·HSIS는 현재 생성 대상이라기보다 파싱·정규화·연결 대상이다. 코드가 형식 차이와 입도 차이를 줄여주지만 내용의 승인 상태까지 자동으로 만들지는 않는다.

기준문서 자동화 전제 구현 기능 기능상 장점 남는 한계 / 승인
SRS / SwRS
추적 허브		 요구 ID, 설명, ASIL, Related ID, 검증기준이 승인 baseline에 존재해야 한다. DOCX 표와 비정형 텍스트에서 요구 ID·ASIL·상위 ID·검증기준을 구조화하고 중복을 제거한다. STS 생성과 전 문서 추적성의 분모를 하나로 맞춰 누락 요구를 표면화한다. 문서에 없는 요구 의도나 안전 목표는 생성하지 못한다. 파싱 성공은 요구 적합성 승인이 아니다.
SDS
설계 기준		 컴포넌트 책임, 인터페이스, ASIL, Related ID와 하위 함수 관계가 식별 가능해야 한다. SwCom/컴포넌트·함수·ASIL·설명을 추출하고, 서로 다른 컴포넌트 설명 충돌 시 임의 상속보다 공백을 선택한다. leaf 함수가 SRS에 직접 연결되지 않아도 함수 → UDS → SDS → SwRS roll-up을 구성할 수 있다. SDS가 이름 목록뿐이면 상위 추적 근거가 약하다. 컴포넌트 책임과 파생·범위제외 근거는 설계 책임자가 확정해야 한다.
HSIS / STP
보강 입력		 HSIS의 신호 ID·SW 변수·방향·특성·Related ID 및 STP 시험전략이 최신 Revision이어야 한다. HSIS 변수와 소스 변수를 연결해 입력 범위·하드웨어 신호·요구 ID를 보강하고 STP의 시험전략을 AI 컨텍스트로 제공한다. 테스트 값이 단순 이름 추정에 머무르지 않고 인터페이스 정의의 min/max와 시험환경을 반영한다. 변수 alias, 단위·스케일, 다중 매핑과 Revision 불일치는 자동 확정할 수 없다.

03 · Specification drafts

문서 4종은 서로 다른 질문을 자동화한다

UDS는 “코드가 무엇을 하는가”, STS는 “요구를 어떻게 검증할 것인가”, SUTS는 “함수 경계와 분기를 어떻게 시험할 것인가”, SITS는 “모듈 사이 상호작용을 어떻게 검증할 것인가”를 초안화한다.

UDS · Unit Design Specification

Source 구조를 함수 단위 상세설계 초안으로 변환

결정론 + 제한형 AI

자동화 전제와 생성 초안

  • C/H 소스가 파싱 가능하고 함수 경계와 prototype이 식별되어야 한다.
  • 함수 ID·이름·prototype·설명·ASIL·Related ID·입출력·전제조건·전역변수·호출·logic flow를 초안화한다.
  • SRS/SDS·주석·함수 override·RAG 근거가 있으면 관련 정보를 보강한다.

코드가 극복하려는 한계

  • AST만으로 놓치는 호출을 함수 body, macro, function pointer, fallback 분석으로 합친다.
  • 헤더 prototype을 우선하고 typedef를 정규화해 구현부 signature의 정보 손실을 줄인다.
  • 설명·ASIL·Related ID마다 comment/SDS/inference 출처를 남긴다.
  • LLM 결과는 evidence schema, reviewer, auditor, judge와 재시도 구조로 점검한다.

구현 기능의 장점

  • 함수 inventory와 호출관계를 수작업보다 빠르고 일관되게 갱신한다.
  • 간접 호출과 전역변수까지 보여주므로 영향분석과 SUTS 입력 품질이 좋아진다.
  • 근거 출처가 남아 추정값과 문서값을 리뷰어가 구분할 수 있다.
  • 동일 소스 Revision에서 반복 생성해 문서 drift를 줄일 수 있다.

초안의 한계와 사람 확정

  • 주석·SDS가 없으면 설명, ASIL, Related ID가 inference 또는 TBD가 될 수 있다.
  • 동적 dispatch, 전처리 분기, 런타임 상태의 실제 의도는 정적 분석만으로 확정할 수 없다.
  • 현재 의미 검증은 confidence를 낮추지만 모든 실패를 hard block하지는 않는다.
  • 안전 의도·ASIL·상위 요구 연결은 설계 책임자가 승인해야 한다.
UDS 자동화는 Source의 함수·호출·입출력·전역상태를 결정론적으로 분석하고, 문서·주석 근거를 결합해 상세설계 검토 초안을 만든다. 추정된 설명·ASIL·Related ID는 출처와 함께 표시하여 사람이 최종 확정한다.

STS · Software Test Specification

승인 요구사항을 SW 요구기반 시험명세 초안으로 변환

SRS 권위 필요

자동화 전제와 생성 초안

  • 실제 요구기반 시험을 위해 승인된 SRS/SwRS 요구 ID와 검증기준이 필요하다.
  • TC ID·제목·안전관련 여부·시험환경·시험방법·전제조건·Action·Expected·SRS ID를 생성한다.
  • SDS·UDS·STP·HSIS를 보조 근거로 사용한다.

코드가 극복하려는 한계

  • SRS 표와 비정형 텍스트를 모두 파싱하고 가장 풍부한 요구 정보를 유지한다.
  • 요구와 함수·logic flow를 매핑해 실행 가능한 단계 후보를 만든다.
  • 함수 미매핑 요구도 삭제하지 않고 review-only TC로 남겨 추적 공백을 숨기지 않는다.
  • 결정론 TC 생성 후에만 AI가 SDS/STP/HSIS 컨텍스트로 문장을 보강한다.

구현 기능의 장점

  • 모든 요구를 TC 후보와 trace matrix에 올려 누락 검토를 빠르게 시작할 수 있다.
  • 요구의 ASIL·상태·상위 ID가 TC 전제조건과 안전 표시로 전파된다.
  • HSIS 신호가 있는 요구는 하드웨어 인터페이스 기반 시험방법을 보강할 수 있다.
  • XLSM, 품질 리포트, 추적 매트릭스를 함께 만들어 문서 작성 시간을 줄인다.

초안의 한계와 사람 확정

  • review-only TC도 요구 매핑 커버리지에는 포함되므로 100%가 실행 가능성이나 시험 적합성을 뜻하지 않는다.
  • Expected result와 환경·판정기준은 요구 의도와 실제 시스템 조건으로 확정해야 한다.
  • AI 응답 검증은 주로 JSON 구조와 길이를 확인하므로 근거 일치까지 보증하지 않는다.
  • 현재 자동 검증기는 생성 열과 검사 열이 어긋나 있어 validation PASS를 단독 신뢰하면 안 된다.
  • SRS가 없으면 STS라기보다 검토용 시험 아이디어 목록으로 표시해야 한다.
STS 자동화는 승인된 SwRS를 분모로 요구별 시험단계와 추적 매트릭스를 생성한다. 함수와 연결되지 않은 요구도 review-only 후보로 남겨 공백을 드러내며, 실행 가능성과 Expected Result는 시험 책임자가 확정한다.

SUTS · Software Unit Test Specification

함수 구조와 경계조건을 단위시험 시퀀스 초안으로 변환

결정론 중심

자동화 전제와 생성 초안

  • 함수 prototype, 입력·출력 또는 관측 가능한 전역상태가 식별되어야 한다.
  • 함수별 TC와 boundary, condition, switch, loop, global-state, void side-effect, MC/DC 시퀀스를 만든다.
  • SRS·UDS·HSIS는 요구 ID, 설명, 인터페이스 범위를 보강한다. SDS 입력은 인터페이스에 선언돼 있으나 현재 본문에서 직접 소비되지 않는다.

코드가 극복하려는 한계

  • 정밀 파싱 실패 시 lightweight parser로 함수 inventory를 보존한다.
  • void/no-param 함수는 callee 입출력, 전역변수, logic-flow 변수까지 추적해 시험 가능한 관측점을 찾는다.
  • HSIS 특성값을 경계값 힌트로 사용하고 타입별 유효·무효 경계를 생성한다.
  • AI는 끝까지 관측 변수를 찾지 못한 함수에만 제한 적용한다.

구현 기능의 장점

  • 반복적인 경계값·분기·loop·switch 조합을 빠짐없이 같은 규칙으로 제안한다.
  • AI 호출 범위를 좁혀 비용과 비결정성을 줄이고 재생성 일관성을 높인다.
  • 전역 side effect와 callee 상태까지 관측 후보로 올려 void 함수의 시험 공백을 줄인다.
  • ASIL과 logic flow를 함께 보므로 MC/DC 검토 대상 선별이 쉬워진다.

초안의 한계와 사람 확정

  • 경계값은 타입·이름·HSIS 힌트 기반이며 실제 알고리즘의 정답 oracle은 아니다.
  • Stub 동작, 초기 전역상태, 타이밍, 허용오차, 테스트 harness는 사람이 확정해야 한다.
  • MC/DC 후보 생성은 독립효과 입증과 목표 커버리지 달성을 보장하지 않는다.
  • 명시적으로 전달한 SDS가 현재 적용되지 않고, 원격 SRS·UDS·HSIS는 로컬 Path.is_file() 검사에서 건너뛸 수 있다.
  • 검증 issue가 있어도 XLSM 생성 자체를 항상 차단하지는 않는다.
SUTS 자동화는 함수의 타입·분기·switch·loop·전역상태를 분석해 경계값과 MC/DC 후보를 결정론적으로 생성한다. AI는 관측점이 부족한 함수에만 제한하며, Expected Result·Stub·독립효과는 시험 책임자가 확정한다.

SITS · Software Integration Test Specification

실제 모듈 간 호출관계를 통합시험 흐름 초안으로 변환

AI 미사용 · 정적 분석

자동화 전제와 생성 초안

  • 소스에서 caller/callee와 파일·모듈 경계가 식별되어야 한다.
  • 통합 flow ID, entry function, call chain, component, 입출력, expected observable, ASIL, Related ID와 sub-case를 생성한다.
  • SRS는 요구 ID, STP는 시험환경을 보강한다. SDS·HSIS는 현재 로드만 하며, UDS 설명 병합도 flow 내용에 주는 효과가 제한적이다.

코드가 극복하려는 한계

  • 프로젝트 내부의 실제 cross-module 호출만 선택하고 OS·library 호출을 제외한다.
  • entry 출력뿐 아니라 pointer out, callee 출력, callee global side effect를 관측값으로 수집한다.
  • 입력이 없으면 callee 입력을, 출력이 없으면 global write를 찾아 통합 관측점을 복원한다.
  • 정렬과 ID 생성이 결정론적이어서 반복 생성 시 차이가 안정적이다.

구현 기능의 장점

  • 문서상의 추상 연결이 아니라 실제 구현 호출을 기반으로 integration 후보를 만든다.
  • 외부 라이브러리 노이즈를 줄이고 SW 컴포넌트 간 인터페이스 검토에 집중한다.
  • pointer와 global side effect를 포함해 관측 가능한 통합 결과를 넓힌다.
  • AI를 아직 사용하지 않아 현재 결과의 재현성과 원인 추적이 명확하다.

초안의 한계와 사람 확정

  • function pointer·callback·runtime dispatch와 더 긴 경로는 정적 call graph에서 빠질 수 있다.
  • Expected 값은 타입 경계 휴리스틱이므로 실제 인터페이스 oracle로 승인할 수 없다.
  • 파일명 기반 모듈 경계와 순번 기반 SwCom_XX가 실제 SDS 컴포넌트와 일치하는지 확정해야 한다.
  • 컴포넌트 경계, timing/order, fault propagation과 stub 구성을 사람이 확정해야 한다.
  • 현재 SDS·HSIS 로딩만으로는 생성 TC가 실제로 보강되지 않는 구간이 있다.
  • cross-module flow가 검출되지 않으면 문서가 생성되지 않으며 원인을 별도 조사해야 한다.

05 · Traceability judgment

자동화의 장점은 수치를 많이 만드는 것이 아니라, 같은 숫자를 다른 의미로 오해하지 않도록 판정축을 분리하는 데 있다.

TRACE MAPPING 연결이 존재하는가? SwRS→SDS/UDS/STS/SUTS/SITS/VectorCAST 링크의 존재와 direct/indirect confidence를 본다.
EXECUTION VERDICT 시험이 실행되어 P/F가 났는가? VectorCAST의 Passed, Failed, Not Executed, Unmatched Result를 분리한다.
STRUCTURAL COVERAGE 코드 구조가 얼마나 실행됐는가? Unit의 Statement/Branch/MC/DC와 Integration의 Function/Function Call을 분리한다.

코드는 10개 밴드 SyRS · SDS · HSIS · UDS · STS · SUTS · SITS · SyTS · SyITS · VectorCAST를 고정하고, 시스템 시험은 SW 시험 판정에서 분리한다. 링크는 같은 입력이면 같은 순서로 정렬되며, ASIL C/D는 SUTS·SITS 누락을 별도 gap으로 표시한다.
